# PostgreSQL. Транзакции, уровни изоляции и аномалии параллельного доступа

## Что такое транзакция

**Транзакция** — это последовательность операций, которая выполняется как единое
целое.

Если все операции завершились успешно — изменения фиксируются.

Если произошла ошибка — все изменения отменяются.

Транзакции позволяют сохранять целостность данных даже при одновременной работе
большого количества пользователей.

Пример:

```sql
BEGIN;

UPDATE account
SET balance = balance - 100
WHERE id = 1;

UPDATE account
SET balance = balance + 100
WHERE id = 2;

COMMIT;
```

Если одна из операций завершится ошибкой, можно выполнить

```sql
ROLLBACK;
```

и база данных вернётся к состоянию до начала транзакции.

---

# ACID-свойства транзакций

Каждая транзакция должна обладать четырьмя свойствами (**ACID**).

## Atomicity (Атомарность)

Транзакция выполняется полностью или не выполняется вовсе.

Нельзя выполнить только часть операций.

---

## Consistency (Согласованность)

После завершения транзакции база данных должна оставаться корректной.

Все ограничения (`PRIMARY KEY`, `FOREIGN KEY`, `CHECK` и др.) должны
сохраняться.

---

## Isolation (Изолированность)

Параллельно выполняющиеся транзакции не должны некорректно влиять друг на друга.

Именно уровни изоляции определяют, какие изменения могут видеть другие
транзакции.

---

## Durability (Надёжность)

После выполнения `COMMIT` изменения сохраняются даже при сбое сервера.

---

# Основные команды транзакций

Начало транзакции:

```sql
BEGIN;
```

Подтверждение изменений:

```sql
COMMIT;
```

Отмена изменений:

```sql
ROLLBACK;
```

---

# Уровни изоляции

Стандарт ANSI SQL определяет четыре уровня изоляции транзакций.

Чем выше уровень изоляции, тем лучше защищены данные от аномалий, но тем ниже
может быть производительность.

| Уровень          | Защита                                            |
| ---------------- | ------------------------------------------------- |
| READ UNCOMMITTED | минимальная                                       |
| READ COMMITTED   | защита от грязного чтения                         |
| REPEATABLE READ  | дополнительно защищает от неповторяющегося чтения |
| SERIALIZABLE     | максимальная защита                               |

> PostgreSQL не использует уровень `READ UNCOMMITTED` отдельно. При его выборе
> фактически применяется поведение уровня `READ COMMITTED`.

Уровень изоляции можно указать при начале транзакции:

```sql
BEGIN ISOLATION LEVEL READ COMMITTED;
```

или

```sql
BEGIN ISOLATION LEVEL REPEATABLE READ;
```

---

# Просмотр текущего уровня изоляции

Проверить текущий уровень можно командой:

```sql
SHOW TRANSACTION ISOLATION LEVEL;
```

# Аномалии параллельного доступа

При одновременной работе нескольких пользователей могут возникать различные
проблемы.

Основные аномалии описаны в стандарте ANSI SQL.

---

# 1. Lost Update (Потерянное обновление)

Возникает, когда две транзакции изменяют одну и ту же строку.

Пример:

**Транзакция A**

```text
rating = 5
```

**Транзакция B**

читает то же значение.

Далее:

```
A → UPDATE rating = 4
```

```
B → UPDATE rating = 3.6
```

Последнее обновление полностью перезаписывает предыдущее.

Изменения первой транзакции теряются.

---

# Lost Update в PostgreSQL

На уровне

```text
READ COMMITTED
```

PostgreSQL использует блокировки строк.

В большинстве случаев потерянное обновление предотвращается автоматически.

На уровне

```text
REPEATABLE READ
```

при конфликте одна из транзакций завершится ошибкой:

```
could not serialize access
```

Её необходимо повторить.

---

# 2. Dirty Read (Грязное чтение)

Возникает, если одна транзакция читает изменения другой транзакции до выполнения
`COMMIT`.

Пример:

Транзакция A

```sql
UPDATE ...
```

ещё не выполнила

```sql
COMMIT;
```

Транзакция B уже видит изменённые данные.

Если первая транзакция выполнит

```sql
ROLLBACK;
```

то вторая уже использовала данные, которых никогда не существовало.

---

## PostgreSQL и Dirty Read

В PostgreSQL грязное чтение невозможно.

Даже уровень

```text
READ UNCOMMITTED
```

работает как

```text
READ COMMITTED.
```

---

# 3. Non-repeatable Read (Неповторяющееся чтение)

Возникает, когда внутри одной транзакции один и тот же запрос возвращает разные
результаты.

Пример:

```sql
SELECT rating
```

↓

Другая транзакция изменяет запись.

↓

Повторный

```sql
SELECT rating
```

возвращает уже другое значение.

---

## READ COMMITTED

На уровне

```text
READ COMMITTED
```

это возможно.

Каждый оператор видит наиболее актуальные данные, которые уже были зафиксированы
(`COMMIT`).

---

## REPEATABLE READ

На уровне

```text
REPEATABLE READ
```

данная аномалия невозможна.

Все запросы внутри транзакции работают с одним и тем же снимком (snapshot)
данных.

---

# 4. Phantom Read (Фантомное чтение)

Возникает, если повторный запрос возвращает другое количество строк.

Например:

```sql
SELECT SUM(rating)
FROM pizzeria;
```

После этого другая транзакция добавляет новую запись:

```sql
INSERT ...
```

Повторный запрос возвращает другую сумму.

Появилась новая строка — "фантом".

---

## READ COMMITTED

Фантомное чтение возможно.

Каждый новый запрос видит уже добавленные строки.

---

## REPEATABLE READ

В PostgreSQL благодаря механизму MVCC повторные запросы работают с тем же
снимком данных, поэтому новые строки не видны до завершения транзакции.

---

# MVCC (Multi-Version Concurrency Control)

PostgreSQL использует механизм **MVCC** — многоверсионное управление
конкурентным доступом.

Главная идея:

При изменении строки PostgreSQL не перезаписывает её сразу, а создаёт новую
версию записи.

Благодаря этому:

- чтение практически не блокирует запись;
- запись не блокирует чтение;
- каждая транзакция получает собственный согласованный снимок данных.

Именно MVCC обеспечивает высокую производительность PostgreSQL при большом
количестве одновременно работающих пользователей.

---

# Snapshot (Снимок данных)

При начале транзакции PostgreSQL формирует снимок базы данных.

На уровнях

- `REPEATABLE READ`;
- `SERIALIZABLE`

все запросы внутри транзакции работают именно с этим снимком.

Поэтому повторный запрос возвращает одинаковый результат.

---

# SERIALIZABLE

Самый строгий уровень изоляции.

Он гарантирует такой результат, как если бы все транзакции выполнялись
последовательно, одна за другой.

Если PostgreSQL обнаруживает потенциальный конфликт между транзакциями, одна из
них завершается ошибкой:

```
could not serialize access due to concurrent update
```

Приложение должно повторить выполнение такой транзакции.

---

# Deadlock (Взаимоблокировка)

Deadlock возникает, когда две транзакции ожидают освобождения ресурсов друг
другом.

Пример.

**Транзакция A**

```text
Блокирует строку 1
```

↓

пытается изменить строку 2.

---

**Транзакция B**

```text
Блокирует строку 2
```

↓

пытается изменить строку 1.

Получается замкнутый круг:

```
A ждёт B
```

```
B ждёт A
```

Ни одна транзакция не может продолжить работу.

---

## Как PostgreSQL решает Deadlock

Сервер автоматически обнаруживает взаимоблокировку.

После обнаружения одна из транзакций завершается ошибкой:

```
deadlock detected
```

Вторая продолжает выполнение.

---

# Как избежать Deadlock

Самый распространённый способ:

Всегда захватывать ресурсы в одинаковом порядке.

Например, если все транзакции сначала изменяют запись с `id = 1`, а затем с
`id = 2`, взаимоблокировка не возникнет.

Также рекомендуется:

- сокращать время выполнения транзакций;
- не удерживать блокировки дольше необходимого;
- выполнять только необходимые операции внутри транзакции.

---

# Новые виды аномалий

Помимо классических аномалий ANSI SQL существуют и более сложные проблемы,
связанные с проектированием и многопользовательской работой.

Наиболее известные:

- Read Skew (перекос чтения);
- Write Skew (перекос записи);
- Serialization Anomaly;
- Fan Trap;
- Chasm Trap;
- циклические зависимости данных.

Большинство из них относятся уже не столько к самим транзакциям, сколько к
особенностям модели данных и сложным сценариям конкурентной работы.

# Сравнение уровней изоляции

| Аномалия            |           READ COMMITTED            |             REPEATABLE READ             | SERIALIZABLE  |
| ------------------- | :---------------------------------: | :-------------------------------------: | :-----------: |
| Dirty Read          |                 ❌                  |                   ❌                    |      ❌       |
| Non-repeatable Read |                 ✅                  |                   ❌                    |      ❌       |
| Phantom Read        |                 ✅*                 |    ❌ (в PostgreSQL благодаря MVCC)     |      ❌       |
| Lost Update         | Защищён механизмом блокировок строк | Конфликт приводит к ошибке сериализации | Полная защита |

> *В PostgreSQL поведение фантомных чтений отличается от классического стандарта
> ANSI SQL благодаря механизму MVCC.

# Практические рекомендации

- Всегда объединяйте связанные изменения в транзакции.
- Используйте `COMMIT` только после успешного завершения всех операций.
- При возникновении ошибки выполняйте `ROLLBACK`.
- Выбирайте минимальный уровень изоляции, который обеспечивает корректность
  данных — более высокие уровни увеличивают вероятность конфликтов и снижают
  производительность.
- Используйте `REPEATABLE READ` и `SERIALIZABLE` только там, где действительно
  необходима строгая согласованность данных.
- Проектируйте транзакции так, чтобы они выполнялись быстро и удерживали
  блокировки минимальное время.
- Захватывайте ресурсы в одинаковом порядке во всех транзакциях, чтобы избежать
  взаимоблокировок.
- Обрабатывайте ошибки сериализации и взаимоблокировок на уровне приложения,
  повторяя транзакцию при необходимости.

# Итоги

После изучения темы необходимо понимать:

- что такое транзакция и какие свойства ACID она обеспечивает;
- как работают команды `BEGIN`, `COMMIT` и `ROLLBACK`;
- какие существуют уровни изоляции и чем они отличаются;
- как проверить текущий уровень изоляции;
- что такое аномалии `Lost Update`, `Dirty Read`, `Non-repeatable Read` и
  `Phantom Read`;
- как PostgreSQL использует механизм MVCC и снимки данных (snapshot) для
  обеспечения согласованности;
- как работает уровень изоляции `SERIALIZABLE` и почему могут возникать ошибки
  сериализации;
- что такое взаимоблокировка (Deadlock), как PostgreSQL её обнаруживает и какие
  приёмы помогают её избежать;
- почему при проектировании многопользовательских приложений важно учитывать
  параллельный доступ к данным и выбирать подходящий уровень изоляции.
