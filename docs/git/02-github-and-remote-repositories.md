# 2. GitHub и удаленные репозитории

Удаленный репозиторий — копия Git-репозитория на сервере. Он нужен для резервной
копии, совместной работы и публикации проектов. GitHub — популярная платформа,
но те же команды применимы к GitLab, Bitbucket и собственному Git-серверу.

## SSH-доступ к GitHub

SSH-ключ позволяет подтверждать доступ без ввода пароля при каждом `push`.
Проверьте, есть ли уже ключ:

```bash
ls -la ~/.ssh
```

Если подходящего ключа нет, создайте новый и добавьте публичную часть в GitHub:

```bash
ssh-keygen -t ed25519 -C "you@example.com"
cat ~/.ssh/id_ed25519.pub
ssh -T git@github.com
```

Содержимое файла с расширением `.pub` можно добавить в GitHub: **Settings → SSH
and GPG keys → New SSH key**. Никому не передавайте файл без `.pub` — это
приватный ключ.

## Публикация локального проекта

Сначала создайте на GitHub пустой репозиторий, например `git-practice`. Не
добавляйте на сайте README или `.gitignore`, если такие файлы уже есть локально.
Затем в локальном проекте выполните:

```bash
git remote add origin git@github.com:<ваш-логин>/git-practice.git
git branch -M main
git push -u origin main
```

`origin` — принятое имя основного удаленного репозитория. Флаг `-u` связывает
локальную ветку `main` с `origin/main`; дальше достаточно использовать
`git push` и `git pull`.

Проверить адреса и состояние синхронизации помогут команды:

```bash
git remote -v
git branch -vv
git status
```

## Клонирование существующего проекта

Когда репозиторий уже находится на GitHub, вместо `git init` используют
`git clone`:

```bash
git clone git@github.com:<ваш-логин>/git-practice.git
cd git-practice
git status
```

Клонирование скачивает историю, создает рабочую директорию и автоматически
настраивает `origin`.

## Получение и отправка изменений

Обычный цикл работы с удаленным репозиторием:

```bash
git pull --ff-only   # получить изменения перед началом работы
# изменить файлы, проверить diff, сделать коммит
git push             # отправить свои коммиты
```

`git pull --ff-only` безопаснее обычного `pull` для новичка: команда завершится
с ошибкой, если Git не может просто сдвинуть ветку вперед. В такой ситуации
нужно разобраться с расхождением истории, а не создавать merge-коммит
автоматически.

Если удаленная ветка изменилась после вашего последнего получения данных,
`git push` будет отклонен. Сначала получите изменения, разрешите возможные
конфликты, создайте коммит и повторите отправку.

## Ветки и pull request

Для новой задачи удобно работать в отдельной ветке:

```bash
git switch -c docs/add-installation-guide
# внести изменения и сделать коммит
git push -u origin docs/add-installation-guide
```

После `push` GitHub предложит открыть pull request (PR). В PR видна разница с
целевой веткой, обсуждения и статус автоматических проверок. Хороший PR содержит
небольшую логичную задачу, понятный заголовок и краткое описание: что изменено,
как это проверено и есть ли важные ограничения.

После проверки изменения объединяют с `main`. Локальную копию обновляют:

```bash
git switch main
git pull --ff-only
git branch -d docs/add-installation-guide
```

## Open source и портфолио

Публичный репозиторий — удобный способ показать проекты. Добавьте понятный
`README.md`: назначение проекта, требования, запуск, примеры и способ проверки.
Не отправляйте в публичный репозиторий пароли, токены, ключи и файлы `.env` с
реальными секретами.

Чтобы внести вклад в чужой проект, обычно делают fork через интерфейс GitHub,
клонируют свою копию, создают ветку, отправляют ее в свой fork и открывают PR в
исходный проект. Перед началом всегда прочитайте `CONTRIBUTING.md` и правила
проекта.

## Практика

Опубликуйте репозиторий из первой темы на GitHub. Создайте ветку, добавьте в
README короткую инструкцию запуска, отправьте ее и откройте PR. Даже если вы
работаете в одиночку, это хорошая тренировка процесса командной разработки.
