# 1. Git: основы и рабочий процесс

Git — распределенная система контроля версий. Она хранит историю изменений
проекта и помогает безопасно работать с кодом в одиночку и в команде. Git не
заменяет GitHub: Git работает локально на компьютере, а GitHub — один из
сервисов для хранения удаленных репозиториев.

## Зачем нужен Git

- сохранять понятную историю проекта;
- возвращаться к рабочей версии после ошибки;
- работать над задачами в отдельных ветках;
- синхронизировать код с командой и публиковать проекты в портфолио.

## Главная модель Git

У Git есть три области:

```text
Рабочая директория  →  Индекс (staging area)  →  Локальный репозиторий
       файл              git add                   git commit
```

Рабочая директория — файлы, которые мы редактируем. Индекс — список изменений,
которые войдут в следующий коммит. Коммит — сохраненная точка в истории
локального репозитория. Это разделение позволяет подготовить только нужные
файлы, а не отправлять в коммит все подряд.

## Первоначальная настройка

После установки Git укажите имя и почту. Они попадут в авторство новых коммитов:

```bash
git --version
git config --global user.name "Ваше Имя"
git config --global user.email "you@example.com"
git config --global init.defaultBranch main
git config --global --list
```

Для GitHub лучше использовать тот же адрес почты, который добавлен в настройках
аккаунта. Не публикуйте в коммитах личные или рабочие адреса, если это
нежелательно: GitHub позволяет использовать специальный адрес `noreply`.

## Создание первого репозитория

Создадим небольшой проект `git-practice`:

```bash
mkdir git-practice
cd git-practice
git init
printf '# Git practice\n' > README.md
git status
```

`git init` создает скрытую папку `.git`. В ней находится история и настройки
репозитория. Не удаляйте и не редактируйте ее вручную.

`git status` — самая полезная команда в начале работы. Она отвечает на три
вопроса: на какой ветке мы находимся, какие файлы изменены и что уже
подготовлено к коммиту.

## Первый коммит

```bash
git add README.md
git status
git commit -m "docs: add project readme"
git log --oneline
```

`git add` добавляет текущую версию файла в индекс. После этого можно изменить
файл еще раз: новое изменение не войдет в коммит, пока его снова не добавить.
`git commit` создает запись в истории из содержимого индекса.

Хороший коммит описывает одно законченное изменение. Сообщение должно отвечать
на вопрос «что сделано»: `docs: add installation guide`,
`fix: handle empty
config`. Формат Conventional Commits необязателен, но
помогает сделать историю понятной.

## Повседневный цикл работы

```bash
# 1. Посмотреть состояние
git status

# 2. Изменить файлы и проверить разницу
git diff

# 3. Выбрать изменения для коммита
git add README.md

# 4. Проверить именно то, что попадет в коммит
git diff --staged

# 5. Сохранить точку в истории
git commit -m "docs: describe project goal"
```

Перед коммитом особенно важно выполнять `git diff --staged`: так можно заметить
случайно добавленный файл, секрет или незаконченный фрагмент.

## Коммиты, HEAD и ветки

Каждый коммит хранит ссылку на предыдущий, поэтому история образует цепочку.
`HEAD` — указатель на текущий коммит. Ветка — именованный подвижный указатель на
последний коммит своей линии истории. По умолчанию главная ветка обычно
называется `main`.

```bash
git log --oneline --graph --decorate --all
git branch --show-current
```

Для отдельной задачи создают ветку, а после проверки объединяют ее с `main`.
Подробно это будет полезно разобрать после освоения базового цикла работы.

## Мини-практика

1. Создайте репозиторий с `README.md`.
2. Сделайте коммит с описанием проекта.
3. Добавьте файл `notes.txt` с тремя командами Git.
4. Перед вторым коммитом посмотрите `git status`, `git diff` и
   `git diff --staged`.
5. Выведите историю командой `git log --oneline`.

В итоге в истории должно быть два осмысленных коммита, а `git status` должен
сообщить, что рабочая директория чистая.
